## Phase Goal

**As a** solo owner, **I want to** run an Arabic RTL app on real phones with a sync-ready database and proven native integrations, **so that** feature work never rests on guesses.

<objective>
Build the two spike widgets (FND-09, D-08): an Android react-native-android-widget that renders from SQLite in a headless task, an iOS expo-widgets widget fed by props the app pushes, one pushSpikeWidget function per platform, and a deep-link tap on both that lands on the spike route with from=widget.

Purpose: widgets are the riskiest native piece of v1 (CLAUDE.md section 3); this plan makes both data paths and both tap paths concrete so plan 01-15 only has to build, add the widget and tap it (or execute the D-09 fallback if needed). Plan 01-14 adds the spike screen that the tap opens, the widget spike rows and the from-widget banner.
Output: Android widget view, headless handler and registration, iOS widget, push functions, wiring tests, spike constants.

No package or app.json change: plan 01-06 installed both widget plugins, plan 01-07 configured widget name RoiSpike, and plan 01-09 added the widget fonts. Runs in parallel with plans 01-11 (database) and 01-12 (telemetry): no shared files.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| App data to home and lock screen | Widget content is visible without unlocking the app |
| Headless widget task to on-device database | Android runs app JS without UI and opens the database |
| Deep link into the app | Any app can open the roi scheme URL |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-26 | Information disclosure | Widget content and the headless handler | low | mitigate | Spike widgets show a public fixture verse and a counter only; the handler reads one settings row through its own connection and never throws; privacy-safe widget defaults are WDG-05 in a later phase |
