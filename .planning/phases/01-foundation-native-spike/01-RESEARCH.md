## User Constraints (from CONTEXT.md)

### Locked Decisions

**Repo layout & tooling**
- **D-01:** Monorepo (apps: mobile, backend, admin; `packages/shared`) using **bun workspaces** with the **isolated linker** (`linker = isolated`) so Tailwind 3 (mobile) and Tailwind 4 (admin) never hoist into each other. Verify in the spike that Metro and native autolinking resolve under isolated installs; if not, fall back to "pin + verify in CI". — **Reversibility:** costly — changing package manager/linker touches every workspace and lockfile.
- **D-02:** `packages/shared` is consumed as **source TypeScript, no build step** by mobile (Metro), backend (Nest) and admin (Vite). It must stay pure TS with no Node-only APIs.
- **D-03:** Test runner is **Vitest** (shared package, backend, admin, fixture-DB migration tests via better-sqlite3 in Node).

**Scripture type & look**
- **D-04:** Scripture font is **decided in the spike**: bundle two candidates (e.g. Amiri vs Noto Naskh Arabic / Scheherazade New) on the torture-fixtures screen and pick after viewing on real phones.
- **D-05:** UI font (buttons, labels, prayer/gratitude text) is a clean sans: **IBM Plex Sans Arabic or Noto Sans Arabic**, distinct from Scripture's naskh.
- **D-06:** Scripture font size is a **5-step stepped slider**, stored in MMKV, applied through a context so all Scripture text scales together.
- **D-07:** Visual feel for theme tokens: **warm, calm, paper-like**; cream/ivory light mode, deep warm-charcoal dark mode, muted gold/olive accent. Phase 1 sets tokens only.

**Spike screen & fallbacks**
- **D-08:** Dev-only **spike screen with live self-test rows** per integration (MMKV write+read, test crash, test analytics event, Google sign-in, widget update, Reanimated), showing pass/fail with error text. Gated/removed before release.
- **D-09:** **Timebox then fall back**: one focused attempt plus one retry with fixes on a real device; if still failing switch to the documented fallback (NativeWind→Uniwind, expo-widgets→@bacons/apple-targets, ts-fsrs 6→5.4.2, Tiptap markdown→hand-written serializer) and record the decision.
- **D-10:** **Torture-fixtures screen** uses real fully-voweled verses plus edge cases: `{الاسم}` token names, mixed Arabic/Latin/digits, alef/hamza/taa-marbuta variants, long lines, and a search box. The same fixtures feed unit tests.

**Schema & event conventions**
- **D-11:** Client IDs are **UUIDv7** (time-ordered), generated by a small pure-TS function in the shared package. — **Reversibility:** one-way — IDs are baked into synced/backed-up user data.
- **D-12:** Timestamps (`createdAt`, `updatedAt`, `deletedAt`) are **integer epoch milliseconds, UTC**. Local-day logic (gratitude day, week starting Saturday) uses a separately stored local date where needed. — **Reversibility:** one-way — format is baked into device DBs and Drive merge.
- **D-13:** Events (prayed, review) live in **separate append-only tables** (e.g. prayer_events, review_events) with UUID + parent id + timestamp, never edited; counts are COUNT queries; undo writes a tombstone on the event; merge is a union by id.
- **D-14:** Migration test uses **a checked-in SQLite fixture per released schema version** with sample rows; the test copies it, runs all pending Drizzle migrations, and asserts data survives intact (Vitest + better-sqlite3). Add a new fixture with every published schema version.

## Summary

Phase 1 has two halves that should be planned as independent tracks. **Track A (pure, Node-testable, no device):** the monorepo skeleton, `packages/shared` (UUIDv7, `normalizeArabic`, Arabic-Indic digits and date formatting, `personalize`, period/seed, `mergeRecords`, zod schemas), the Drizzle schema with the sync-ready column convention, event tables, the fixture-DB migration test, and guard tests (schema introspection, Tailwind-major resolution, forbidden imports and forbidden physical-direction classes). I verified in this session that the exact migrations folder `drizzle-kit generate` emits for `driver: 'expo'` also applies cleanly with `drizzle-orm/better-sqlite3/migrator` on Node 26 with `better-sqlite3@13.2.0`, so D-14 is a straightforward design. **Track B (device-bound):** one Expo SDK 58 app with every native dependency, an EAS development build and an EAS internal release build on a real iPhone and a real Android phone set to English, a dev-only spike screen, a torture-fixtures screen, and telemetry wiring that sends a test crash and a test event.

The dominant risks are all in Track B and are all explicitly timeboxed by D-09: bun isolated linker versus Metro/autolinking, RNFB 27 (SPM-only, dynamic frameworks) coexisting with Google Sign-In 17 (SPM) and MMKV 4 (Nitro), the SDK 58 scene-based iOS lifecycle versus Google URL callbacks, and `expo-widgets` RTL/tap behavior. The documented facts that most affect planning: `expo-widgets` runs in an isolated runtime (no imports, no module scope, props push only) and its SwiftUI `EnvironmentConfig` does **not** include `layoutDirection`, so RTL inside the iOS widget is a genuine spike question with the `@bacons/apple-targets` fallback ready; `react-native-android-widget` renders React views to a **bitmap** (so Arabic shaping is done by RN text rendering, fonts come from the plugin's `fonts` option, and it needs exact widget size); `expo-font`'s config plugin names fonts by **file name on Android but by the name inside the file on iOS**, so font files must be renamed to their PostScript names.

Several human-only prerequisites gate the whole device track and must be planned as `checkpoint:human-action` tasks before any task that needs them: bundle id / package name / app group / URL scheme decision, Firebase project with both apps, Google OAuth clients (iOS client + Android client with the EAS keystore SHA-1), Apple App ID + App Group + iPhone UDID registration, and having an iPhone and an Android phone physically available (none were connected during this research).

**Primary recommendation:** Plan two parallel tracks. Start Track A and the human prerequisites immediately (Wave 1); do the Expo app scaffold and plugin configuration in Wave 2; run the EAS dev build and each integration row in Wave 3 with the D-09 timebox; finish with one end-of-phase human-verify checkpoint on both phones (matches `human_verify_mode: end-of-phase`).

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Forced RTL, locale, digits | Native config (plugin, build time) | Shared pure TS (digit/date formatters) | `forcesRTL` and `CFBundleLocalizations` are binary-level; digits are formatted by our own function, not `Intl` |
| Scripture font + size | Native assets (embedded TTF) | Browser/Client (RN) context + MMKV | Fonts embed at build time; size step lives in a React context |
| Theme / dark mode | Client (NativeWind CSS variables) | Native (`userInterfaceStyle`) | Tokens are JS/CSS; OS appearance only seeds the default |
| Arabic search normalization | Shared package (pure TS) | Database (`searchText` column, later phases) | Same function must run on app, backend import and admin |
| ID/timestamp/tombstone conventions | Database (Drizzle schema) | Shared package (`uuidv7`, `mergeRecords`) | Conventions are column-level; generation and merge are pure functions |
| Event counters | Database (event tables + COUNT) | Client repo layer (later phases) | Derived, never stored |
| Telemetry allowlist + scrubbing | Client (one `telemetry/` module) | Native Firebase SDKs | Single choke point is the only enforceable privacy control |
| iOS widget rendering | Native (WidgetKit extension via `expo-widgets`) | Client (props push from app) | Widget cannot query anything; app pushes display props |
| Android widget rendering | Native (RNAW provider) | Client headless JS task (reads expo-sqlite) | Handler may open the DB read-only; renders view to image |
| Google Sign-In | Native SDK (via RN lib) | Client JS (`getTokens`) | Phase 1 proves interactive sign-in only; headless token is Phase 8 |
| Test running | Node (Vitest + better-sqlite3) | — | Runs under real Node, not the Bun runtime |

### Pattern 1: Sync-ready table convention (one helper + one guard)

**What:** Every user-data table spreads `syncCols()`; a test introspects the whole schema and fails if any non-allowlisted table lacks `id`, `created_at`, `updated_at`, `deleted_at` (or has an auto-increment PK). Event tables carry the same four columns (D-13: events are never edited; "undo" sets `deletedAt` and bumps `updatedAt` so LWW/union merge propagates the tombstone).
**When to use:** every table added in any later phase (this is what stops Pitfall 1 from re-appearing).
**Recommended Phase 1 tables:** `settings`, `mem_verses` (nullable `fsrs` JSON + `fsrs_model`, per CLAUDE.md), `review_events`, `prayers`, `prayer_events`, `gratitude_lines` (deterministic id `shukr:{yyyy-mm-dd}`). Later phases add `favorites`, `assigned_verses`, `user_items`, `recordings`, `people` with the same helper. Before the first published build there are no installed databases, so the baseline migration may be regenerated freely; the D-14 fixture rule begins at the first TestFlight/Play-internal build, but ship `fixtures/v1.sqlite` now to prove the harness.
**Example:** see Code Examples.

### Pattern 2: Forced RTL is build-time, verified at runtime

**What:** `expo-localization` plugin `forcesRTL: true` ("forces RTL layout regardless of device language") plus iOS `CFBundleDevelopmentRegion: "ar"` / `CFBundleLocalizations: ["ar"]` and Android `supportsRtl`. No JS `forceRTL()`/restart dance. The spike screen shows `I18nManager.isRTL` and `getLocales()[0].languageTag` side by side so a phone in English visibly proves the criterion. Fallback if `isRTL` is false on first launch: JS `I18nManager.forceRTL(true)` + reload (record in decision note).
**Source:** [CITED: docs.expo.dev/versions/latest/sdk/localization: `forcesRTL` default false; options "require building a new app binary"]. The docs say nothing about first-launch restart behavior, so this is verified only on-device (A2).

### Pattern 3: Fonts embedded by plugin, named by PostScript name

**What:** `["expo-font", { "fonts": ["./assets/fonts/Amiri-Regular.ttf", ...] }]`. On Android the font family name = **file name**; on iOS it is **read from inside the file** [CITED: docs.expo.dev/versions/latest/sdk/font]. So rename each TTF to its PostScript name (`Amiri-Regular.ttf`, `Amiri-Bold.ttf`, `ScheherazadeNew-Regular.ttf`, `IBMPlexSansArabic-Regular.ttf`, ...) and use that string as `fontFamily` on both platforms; verify each with `Font.getLoadedFonts()` on the spike screen. Use **static** per-weight files only (`@expo-google-fonts/*` tarballs ship statics: Amiri 400/700 + italics; Scheherazade New 400/500/600/700; IBM Plex Sans Arabic 100-700; Noto Naskh 400-700 [VERIFIED: npm tarballs listed this session]). Commit the TTFs and their OFL licence texts; do not depend on the `@expo-google-fonts/*` packages at runtime.
**Recommended D-04 candidates:** Amiri vs Scheherazade New (both built for fully vowelled text; Noto Naskh as an optional third). **UI font (D-05):** IBM Plex Sans Arabic Regular/Medium/Bold (3 weights only).
**Text rules:** `lineHeight` >= 1.7x font size for voweled Scripture; **never** `letterSpacing`/`tracking-*` on Arabic (breaks joining) [A, Pitfall 6 in research/PITFALLS.md, tagged T there]; `writingDirection: 'rtl'`.

### Pattern 4: Scripture size = 5 discrete steps

**What:** `ScriptureSizeProvider` reads/writes an integer step 0..4 in MMKV (`createMMKV()`), maps it to `{fontSize, lineHeight}` from a constant table (e.g. 18/20/23/27/32 px with lineHeight = 1.8x), and a `<Scripture>` text component consumes the context. The control is five `Pressable` dots (logical order, RTL-safe), not a gesture slider (YAGNI; avoids gesture direction bugs). Cap OS font scaling with `maxFontSizeMultiplier` (e.g. 1.3) so the in-app step stays authoritative. [ASSUMED values, design discretion]

### Pattern 5: Theme tokens as CSS variables

**What:** `global.css` defines `:root` and `.dark` token sets, `tailwind.config.js` maps semantic names (`background`, `foreground`, `card`, `muted`, `accent`, `border`) to `hsl(var(--x))`, `darkMode: 'class'`, user preference in MMKV (`system|light|dark`) applied via NativeWind's color-scheme setter, `userInterfaceStyle: "automatic"` in app config [A11]. Suggested values (design discretion): light bg `#FAF6EC`, ink `#2B2620`; dark bg `#1E1B17`, text `#EDE6D6`; accent muted gold-olive `#8A7A3B` (light) / `#C2B26A` (dark). Accent on ivory is only about 3.9:1, so use it for large text/icons/borders, never body text. Phase 1 sets tokens only (D-07).

### Pattern 6: Telemetry choke point

**What:** One module is allowed to import `@react-native-firebase/*`. API surface: `track(name: AllowedEvent): void` (no params at all), `reportError(code: ErrorCode): void` (builds `new Error(code)`; never forwards original messages), `setTelemetryConsent(bool)`. `firebase.json` sets auto-collection off for both products; the spike screen has a dev toggle to enable collection. Modular API only: `getAnalytics()`, `logEvent(analytics, name, params)`, `setAnalyticsCollectionEnabled(analytics, true)`, `getCrashlytics()`, `crash(crashlytics)`, `recordError`, `setCrashlyticsCollectionEnabled` [CITED: rnfirebase.io/analytics/usage, /crashlytics/usage].
**Closed event list (Claude's discretion, proposal):** `spike_test`, `onboarding_completed`, `first_win_reached`, `review_session_completed`, `prayer_logged`, `gratitude_saved`, `drive_backup_connected`. No parameters, names match `^[a-z][a-z0-9_]{0,39}$`, none starts with `firebase_`, `google_` or `ga_` [A7].
**Enforcement:** a Vitest guard that scans `apps/mobile/{app,src}` and fails on `@react-native-firebase/(analytics|crashlytics)` imports outside `src/telemetry/`.

### Pattern 7: Widget data flow in Phase 1

- **iOS (`expo-widgets`):** one spike widget; app calls `SpikeWidget.updateSnapshot({ verse, count })`. Component body must start with the `'widget'` directive, use only `@expo/ui/swift-ui` components, no hooks/imports/module-scope values; on iOS 17+ root needs `containerBackground(..., 'widget')` [CITED: docs.expo.dev/versions/latest/sdk/widgets]. Tap target via `widgetURL('roi://spike')` (one per widget; "supported on iOS and tvOS") [CITED: docs.expo.dev/versions/latest/sdk/ui/swift-ui/modifiers].
- **Android (`react-native-android-widget`):** plugin config in `app.config.ts` (`fonts: [...]`, `widgets: [{ name, minWidth, minHeight, updatePeriodMillis >= 1800000 }]`); `registerWidgetTaskHandler` runs at JS load; handler reads the spike row from expo-sqlite in a separate connection and calls `props.renderWidget(<SpikeWidget .../>)`; tap via `clickAction="OPEN_URI"` + `clickActionData={{ uri: 'roi://spike' }}` (requires Android 7+ and expo-router deep linking) [CITED: RNAW docs `handling-clicks.md`, `register-widget-expo.md`]. The library renders RN views to an **image** and needs the exact widget size [CITED: RNAW docs `limitations.md`].
- Keep `expo-widgets` `enableAndroid: false` (default) so only one system creates Android widgets [CITED: expo-widgets docs: `enableAndroid` default false].

### Anti-Patterns to Avoid

- **Importing anything from `expo-*`/`react-native` in `db/schema.ts` or `packages/shared`:** breaks Node tests and D-02.
- **Calling `analytics()`/`crashlytics()` outside `telemetry/`**, passing free-form params, or using `usePathname()` as a screen name.
- **Editing a published migration** or generating migrations with `drizzle-kit push` for anything but a throwaway.
- **Physical-direction classes** (`ml-`, `mr-`, `pl-`, `pr-`, `left-`, `right-`, `text-left`, `text-right`) and `tracking-*` in mobile source. Guard test, not review discipline.
- **Hand-editing `ios/` or `android/`** (config plugins only; prebuild regenerates them).
- **Running Vitest with `--bun`** (better-sqlite3 needs real Node).
- **Opening the main SQLite file from the iOS widget extension** (props push only).

| Migration runner (tests) | Custom fixture applier | `drizzle-orm/better-sqlite3/migrator` `migrate(db, {migrationsFolder})` | [VERIFIED: ran on Node 26.13, created `__drizzle_migrations` + table] |

**Key insight:** in this phase the dangerous things to hand-roll are native glue (widgets, Firebase, fonts, RTL); the things you *should* own are tiny pure functions whose behavior must be identical on app, backend and admin.

## Common Pitfalls

### Pitfall 1: bun isolated linker breaks Metro or native autolinking
**What goes wrong:** Metro cannot resolve a transitive dep, or a native module is not autolinked; or a package that "assumes a flat layout" fails [CITED: bun.com/docs/pm/isolated-installs known limitations; docs.expo.dev/guides/monorepos: "not all packages you install will work"].
**Why it happens:** isolated installs do not hoist; Expo supports isolated installs only from SDK 54 (we are on 58) [CITED].
**How to avoid:** first build is the test. Try isolated; on failure, change only `bunfig.toml` to `linker = "hoisted"` (Bun reinstalls from scratch) and enforce Tailwind separation with the guard test below instead. Do not hand-write `watchFolders`/`nodeModulesPaths` (Expo configures Metro for monorepos automatically) [CITED].
**Warning signs:** `Unable to resolve module` for a dep that is in `package.json`; pods missing a module after `prebuild`.

### Pitfall 2: Tailwind majors collapse into one
**What goes wrong:** mobile silently resolves Tailwind 4 (or admin resolves 3). `nativewind@4.2.7` declares peer `tailwindcss: ">3.3.0"`, which Tailwind 4 satisfies [VERIFIED: npm], so the peer range will not protect you.
**How to avoid:** guard test that `require.resolve('tailwindcss/package.json', { paths: [apps/mobile] })` has major 3, and from `apps/admin` major 4 (admin declares Tailwind 4 only when Phase 3 starts; assert admin does NOT resolve 3). Pin `tailwindcss@3.4.19` exactly in mobile.

### Pitfall 3: Font family names differ per platform
See Pattern 3. Symptom: Scripture renders in the fallback font on one OS only. Rename files to PostScript names, verify via `getLoadedFonts()`, check **bold** separately (separate family per weight; `fontWeight` alone does not select a file).

### Pitfall 4: RNFB 27 + Google Sign-In dependency-manager mismatch
**What goes wrong:** `pod install`/prebuild fails or duplicate symbols. RNFB 27 is SPM-only and needs dynamic frameworks; Google Sign-In must use the same dependency manager; `disableSPM: true` and `useFrameworks: "static"` both fail [CITED: rnfirebase.io Expo page; react-native-google-signin.github.io/docs/setting-up/expo: "Firebase and Google Sign-In must use the same dependency manager", `iosDependencyManager`: `"auto" | "cocoapods" | "spm"`, default `"auto"`]. Set `"spm"` explicitly.
**Also:** if a dev build was installed before RNFB was added, uninstall it first or you get `RNFBAppModule not found` [CITED].

### Pitfall 5: Crashlytics test produces nothing
**What goes wrong:** crash does not appear. `crash()` does nothing when collection is disabled; debug builds do not report unless `crashlytics_debug_enabled`; an attached debugger swallows it; the report uploads on the **next launch** [CITED: rnfirebase.io/crashlytics/usage].
**How to avoid:** use the EAS internal **release** build, enable collection via the spike toggle, trigger `crash()`, force-quit, relaunch, wait for the Firebase console. Android Crashlytics config plugin covers only steps 2 and 3 of the Android setup (Google repository and NDK block are not added) [CITED: same page]; confirm the generated project builds a release.

### Pitfall 6: Personal text reaches Crashlytics through JS error messages
**What goes wrong:** an uncaught JS error whose message embeds user text is uploaded as-is. **Whether RNFB auto-reports uncaught JS errors with their original message is not documented in what I fetched (A8).**
**How to avoid:** REL-01 acceptance test with a sentinel: throw `new Error('PRAYER_SENTINEL_تشفع')` from a spike button in the release build and confirm the report does not contain it (if it does, install a `ErrorUtils.setGlobalHandler` wrapper in `telemetry/` that rewrites the error before RNFB sees it, and keep `reportError(code)` as the only sanctioned path). Never log Drizzle bound params outside `__DEV__`.

### Pitfall 7: Analytics test event "does not arrive"
**What goes wrong:** auto-collection is off by design (consent-first), or events are batched. **How to avoid:** the spike toggle calls `setAnalyticsCollectionEnabled(getAnalytics(), true)` before `track('spike_test')`; verify in Firebase DebugView (Android: `adb shell setprop debug.firebase.analytics.app <package>`) or the Realtime view for release builds. iOS DebugView needs a launch argument that EAS builds cannot pass, so for iOS rely on Realtime/Events (A9). Disable automatic screen reporting with `google_analytics_automatic_screen_reporting_enabled: false` in `firebase.json` [CITED]. IDFA: analytics Expo plugin has `withoutAdIdSupport` [CITED: rnfirebase.io Expo page; exact effect under SPM is a spike check (verify no AdSupport linkage)].

### Pitfall 8: SceneDelegate (SDK 58) vs Google Sign-In URL callback
**What goes wrong:** sign-in sheet returns to the app but the promise never resolves (URL delivered to scene, handler registered on app delegate). SDK 58 generates `SceneDelegate.swift` [CITED: CLAUDE.md SDK 58 note]. **How to avoid:** spike row on a real iPhone first; if broken, check the library's v17 notes before any native patching; fallback is a documented-timebox decision, not a hand-edit of `ios/`.

### Pitfall 9: Google OAuth wiring (human-only, easy to get wrong)
iOS needs the reversed-client-ID URL scheme (plugin `iosUrlScheme` or Firebase `GoogleService-Info.plist`). Android needs an OAuth client of type Android with the package name and the **SHA-1 of the EAS-managed keystore** (get via `eas credentials`); a dev build and the internal release build share that keystore, but Play App Signing will differ later (Phase 9). A consent screen left in "Testing" expires grants after 7 days: acceptable for the spike, mandatory to fix before release (REL-04). Request no scope beyond sign-in in Phase 1 (optionally `drive.appdata` via `addScopes` as a stretch row).

### Pitfall 10: expo-widgets runtime restrictions bite late
The widget component has no imports, no module-scope constants, no hooks; everything (strings, colors, the URL) must be inline or in props [CITED]. Do not design a shared helper that the widget file imports. SwiftUI `environment` in `@expo/ui` accepts only `colorScheme | editMode | locale | timeZone` (no `layoutDirection`) [CITED], so RTL inside the widget depends on what the widget extension inherits. This is the specific question the iOS row answers; if Arabic paragraphs/alignment/order are wrong on an English phone after one retry, switch to `@bacons/apple-targets` (D-09) and record it.

### Pitfall 11: Android widget bitmap sizing and fonts
RNAW draws views to an image; sizes reported by some launchers differ from actual size; the library scales and calibrates on first click [CITED: `limitations.md`]. Custom fonts for widgets must be listed in the plugin's `fonts` option (separate from `expo-font`) [CITED: `register-widget-expo.md`]. `updatePeriodMillis` minimum is 30 minutes; push updates from the app with `requestWidgetUpdate()` after DB writes.

### Pitfall 12: Vitest runs under the wrong runtime or wrong Node
The shell here aliases `node` to bun (interactive alias only) and the only real Node installed is 26.13 (Homebrew). `better-sqlite3` works on it (verified), but the owner's target is Node 24 LTS (CLAUDE.md) and EAS's SDK 58 image ships Node 22.23.3 + Bun 1.4.2 [CITED: docs.expo.dev/build-reference/infrastructure]. Add `.node-version` = 24 and `engines`, never use `bun --bun`/`bun test` for these suites, and set `node` in the EAS profile if a build step needs it.

### Pitfall 13: Fixture DB carries WAL side files
A fixture saved in WAL mode leaves `-wal`/`-shm` files or loses recent rows when copied alone. Generate fixtures with `journal_mode = DELETE` (or `VACUUM INTO`) and commit only the `.sqlite` file; the migration test must copy it to a temp path before opening.

### Pitfall 14: Drizzle migrations work in dev and break in release
`.sql` imports need `sourceExts.push('sql')` in Metro and the `inline-import` Babel plugin for `.sql` [CITED: orm.drizzle.team/docs/connect-expo-sqlite]. Verify the **release** build runs `useMigrations` successfully on both phones (add a spike row that reads `__drizzle_migrations` count and inserts/reads a `settings` row).

### Pitfall 15: Timezone-dependent period logic
Compute day/week/month keys from **local date components** (`getFullYear/getMonth/getDate/getDay`), never `toISOString()`. Run the shared suite under at least two zones (e.g. `TZ=Africa/Cairo` and `TZ=America/Los_Angeles`) as separate scripts.

```ts
});

export const prayerEvents = sqliteTable('prayer_events', {   // append-only (D-13)
  ...syncCols(),

  prayedAt: integer('prayed_at').notNull(),
  localDate: text('local_date').notNull(),
}, (t) => [index('prayer_events_parent').on(t.prayerId, t.deletedAt)]);
```

### Fixture-DB migration test (D-14)

```ts
// Verified approach: same ./drizzle folder (driver:'expo') applies via better-sqlite3 migrator on Node 26.13
import Database from 'better-sqlite3';
import { drizzle } from 'drizzle-orm/better-sqlite3';
import { migrate } from 'drizzle-orm/better-sqlite3/migrator';
import { copyFileSync, mkdtempSync } from 'node:fs';
import { join } from 'node:path';
import { tmpdir } from 'node:os';

it.each(['v1'])('fixture %s migrates to latest with data intact', (v) => {
  const dir = mkdtempSync(join(tmpdir(), 'roi-'));
  const file = join(dir, 'db.sqlite');
  copyFileSync(join(__dirname, `../../drizzle/fixtures/${v}.sqlite`), file);
  const sqlite = new Database(file);
  migrate(drizzle(sqlite), { migrationsFolder: join(__dirname, '../../drizzle') });
  expect(sqlite.prepare('select count(*) c from prayers where deleted_at is null').get()).toEqual({ c: 2 });
  expect(sqlite.pragma('integrity_check', { simple: true })).toBe('ok');
});
```

```ts
// uuidv7: RFC 9562 layout [ASSUMED A10]; rand injected so shared stays platform-free
export function uuidv7(now: number, rand: (n: number) => Uint8Array): string {
  const b = Uint8Array.from(rand(16));
  let t = now; for (let i = 5; i >= 0; i--) { b[i] = t % 256; t = Math.floor(t / 256); }
  b[6] = (b[6] & 0x0f) | 0x70; b[8] = (b[8] & 0x3f) | 0x80;
  const h = Array.from(b, (x) => x.toString(16).padStart(2, '0')).join('');
  return `${h.slice(0, 8)}-${h.slice(8, 12)}-${h.slice(12, 16)}-${h.slice(16, 20)}-${h.slice(20)}`;
}
```

```ts
// normalizeArabic: explicit code-point ranges, no \p{} / Intl (Hermes support unverified, A1)
const MARKS = /[\u0610-\u061A\u064B-\u065F\u0670\u06D6-\u06ED\u08D3-\u08FF\u0640]/g;  // tashkeel, Quranic marks, tatweel
const BIDI = /[\u200E\u200F\u202A-\u202E\u2066-\u2069\u061C]/g;  // LRM RLM embeddings isolates ALM
export function normalizeArabic(s: string): string {
  const n = typeof s.normalize === 'function' ? s.normalize('NFC') : s;
  return n.replace(BIDI, '').replace(MARKS, '')
    .replace(/[آأإٱ]/g, 'ا')   // آ أ إ ٱ -> ا
    .replace(/ى/g, 'ي')                        // ى -> ي
    .replace(/ة/g, 'ه')                        // ة -> ه
    .replace(/[٠-٩]/g, (d) => String(d.charCodeAt(0) - 0x0660))   // Arabic-Indic digits
    .replace(/[۰-۹]/g, (d) => String(d.charCodeAt(0) - 0x06F0))   // Persian digits
    .replace(/\s+/g, ' ').trim().toLowerCase();
}
export const toArabicDigits = (v: string | number) => String(v).replace(/\d/g, (d) => String.fromCharCode(0x0660 + Number(d)));
```

```ts
// merge: per-record LWW; deletion wins ties; deterministic tie-break keeps it commutative; clamp future clocks
export interface SyncRow { id: string; updatedAt: number; deletedAt: number | null }
const pick = <T extends SyncRow>(a: T, b: T): T =>
  a.updatedAt !== b.updatedAt ? (a.updatedAt > b.updatedAt ? a : b)
  : (a.deletedAt !== null) !== (b.deletedAt !== null) ? (a.deletedAt !== null ? a : b)
  : JSON.stringify(a) >= JSON.stringify(b) ? a : b;
export function mergeRecords<T extends SyncRow>(local: readonly T[], remote: readonly T[], now: number): T[] {
  const cap = now + 86_400_000, out = new Map<string, T>();
  for (const raw of [...local, ...remote]) {
    const r = raw.updatedAt > cap ? { ...raw, updatedAt: now } : raw;
    const cur = out.get(r.id); out.set(r.id, cur ? pick(cur, r) : r);
  }
  return [...out.values()].sort((a, b) => (a.id < b.id ? -1 : 1));
}
```
Required tests: commutative (`merge(a,b)` equals `merge(b,a)`), idempotent, associative over shuffled inputs, tombstone beats equal-timestamp edit, newer edit beats older tombstone, future-clock clamp, events union by id.
